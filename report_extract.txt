[Heading2] INTRODUCTION
[Heading3] General Introduction
[] Nowadays, software testing is a very important phase in the software development lifecycle. The aim of it is to ensure the reliability and correctness of the software. In modern development practices, major big technology companies have the position or even specific department for software testing. This position or department is responsible for verifying software quality and detecting potential defects.
[] As software continues to grow in scale and complexity, manual testing becomes increasingly time-consuming as they have to plan and compare the actual result with the expected result. This situation has led to the emergence of automated software testing techniques. Automated testing provides several advantages for software development which are the reduction of repetitive work, improved tester productivity, minimization of human errors, and more consistent testing outcomes (Ammann and Offutt, 2016).
[] Currently even though a lot of mature testing tools exist, they are still used as standalone tools which require developers to manually setup and orchestrate. This kind of complex setup is a challenge for students and developers working on academic or small-scale projects. They often struggle at the beginning phase which leads them to skip the testing phase on the software project.
[] Therefore, this software addresses this situation by proposing an automated testing framework specifically designed for Python projects. This software provides a straight-through service such as test generation, test execution, regression text and code coverage analysis. Not only that, the software also provides a graphic user interface to lower the barrier for students and novice developers. They might adopt proper testing practices, reducing manual effort and improving code quality with it.
[Heading3] Importance of the Study
[] The importance of this study is to reduce the learning curve for students and novice developers when implementing testing and the necessary tools. Nowadays, those existing testing frameworks require complex configuration and setup. This complexity has been identified as a key barrier to the adoption of testing practices among developers (Rafique & Mišić, 2013). This technical burden may affect them and cause them to give up on the idea of learning testing. To address this issue, the software system simplifies the configuration process and eliminates unnecessary complexity. This allows users to focus on learning the test design and logical reasoning. 
[] In addition, the system establishes a rapid feedback loop. While supporting efficient development workflows, it helps developers cultivate a quality-oriented mindset. It provides immediate feedback on test results and code coverage metrics. Developers can quickly identify and resolve defects, thereby making testing a natural and continuous part of the development process. This not only encourages the adoption of testing best practices but also reinforces the emphasis on software quality, which is widely recognized as a fundamental principle of modern software engineering (Ammann & Offutt, 2016).
[Heading3] Problem Statement
[] Despite the recognised importance of software testing in ensuring code quality and reliability (Ammann and Offutt, 2016), the practical adoption of systematic testing practices among students and novice developers working on small-scale Python projects remains limited. Recent empirical studies at computing-education venues have begun to quantify this gap. Bai, Smith and Stolee (2021), surveying 54 students from two universities, reported that most students were ineffective in finding known defects in a controlled test-design task, and Showler, Miljanovic and Bradbury (2025), analysing 1014 tests written by 12 student groups in an undergraduate Software Quality Assurance course, found that the test suites produced under required Test-Driven Development practices still contained a disproportionately high number of duplicate and superficial tests. The four sub-sections that follow identify the structural causes of these observed outcomes and connect each cause to one of the three capabilities which are unit testing, regression testing, and code coverage analysis.
[Heading4] Skipped Testing Practices and the Educational Gap in Small-Scale Python Projects
[] The most direct evidence of the adoption gap comes from controlled student studies. Bai et al. (2021) surveyed 54 students from two universities and assigned them black-box and white-box testing tasks using real software projects. They reported that "most students were ineffective in finding known defects" despite being given the test cases they would have written as a reference solution (Bai et al., 2021). This is not an outcome of low motivation: Rafique and Mišić (2013), in a meta-analysis of Test-Driven Development studies, reported that the productivity overhead of disciplined testing practices is a recurring concern in contexts where automated tooling and guidance are absent, indicating that the barrier is structural rather than motivational. Showler et al. (2025) reinforced this conclusion from a complementary angle, finding that even in courses where Test-Driven Development was a mandatory practice, student groups produced test suites with a high proportion of duplicate and happy-path-only tests, suggesting that the requirement to test does not by itself translate into effective test design.
[] The consequence of this bypass is twofold. First, students graduate without internalising testing as a routine practice, leaving them underprepared for industrial roles in which testing competence is expected (Pressman and Maxim, 2020). Second, the iterative code-quality improvements that continuous testing enables are absent from their projects, leading to compounding defects in later development phases. This educational gap directly contradicts the curriculum's intent to produce quality-oriented software engineers and suggests that the resolution requires not additional motivation but a reduction in the structural cost of entry.
[Heading4] Fragmented Toolchains and High Configuration Overhead
[] Even when students recognise the value of testing, the practical setup of a Python testing environment introduces substantial friction. Modern Python testing requires orchestrating at least three independent tools: a test execution framework such as pytest, a coverage measurement tool such as coverage.py, and an optional automated test generation tool such as Pynguin (Lukasczyk and Fraser, 2022). Each tool introduces its own configuration conventions such as pytest.ini or pyproject.toml for pytest, .coveragerc for coverage.py, and command-line arguments for Pynguin. These configurations rarely interoperate without manual coordination. Lukasczyk and Fraser (2022) acknowledged this challenge in their presentation of Pynguin, noting that even experienced researchers find the integration of multiple testing utilities into a single coherent workflow to be a non-trivial engineering task.
[] This overhead is not merely theoretical. Showler et al. (2025) reported that their participating student groups still produced test suites with the structural problems enumerated in 1.3.1 above. Although this study did not explicitly examine configuration overhead as an independent variable, the observations suggest that even with adequate tools, configuration and integration costs remain a significant source of friction during development. For students lacking such course guidance, the mental effort required to understand the configuration models of various tools often outweighs the expected benefits of conducting tests. Consequently, the testing phase is not only neglected but also hindered by setup processes that are difficult for novice developers to handle.
[Heading4] Manual Unit Test Creation as a Knowledge Barrier
[] When students do attempt to write tests, they face a knowledge barrier that compounds the configuration overhead. Effective unit testing requires familiarity with techniques such as equivalence partitioning, boundary value analysis, and coverage criteria. These techniques are typically only introduced in advanced software engineering courses (Ammann and Offutt, 2016). The behavioural signature of this barrier is now well documented. Showler et al. (2025), analysing 1014 tests from 12 student groups, found that the groups were "significantly more likely to test happy paths than invalid inputs" and "inefficiently tested" happy paths and explicit requirements, "resulting in a higher proportion of software tests with duplicate intent" (Showler et al., 2025). Bai et al. (2021) reached a complementary conclusion, identifying six test smells in student-written code and reporting that the most common smells were "ignoring setups in the test code and testing happy path only" (Bai et al., 2021).
[] These inefficiencies are not simply a function of effort. Fraser and Arcuri (2013) demonstrated that automated search-based test generation can produce test suites with branch coverage comparable to, and in some cases exceeding, those written manually by experienced developers, indicating that the manual approach has structural limitations even in expert hands. On real Python code, Lukasczyk and Fraser (2022) reported that Pynguin's DynaMOSA algorithm achieves a mean branch coverage of 67.97% across 118 modules from 17 open-source libraries within a fixed 600-second budget; a random baseline achieves only 63.57% under the same conditions. The gap between these automated data and the behavioral characteristics of student-written tests quantifies the knowledge barriers faced by novice developers and prompts the inclusion of an automated test generation module in the proposed system.
[Heading4]  Invisible Regression Verification and Coverage Interpretation
[] The third barrier affects the two capabilities that students are least equipped to evaluate on their own are regression testing and code coverage analysis. Regression testing requires re-running a previously validated test suite to confirm that recent changes have not introduced new defects (Ammann and Offutt, 2016). In industrial practice this is automated through continuous integration pipelines. While in academic settings, it requires the student to remember the relevant test files, re-execute them manually, and compare outcomes across runs. This process scales poorly with project size and provides no visual cue when a previously passing test has begun to fail.
[] Code coverage analysis compounds this problem in two ways. First, coverage tools such as coverage.py produce their results in command-line tables or static HTML files that list executed and unexecuted line numbers, imposing a significant interpretive burden on beginners. Second, the coverage percentage itself is a poor proxy for test suite effectiveness. Inozemtseva and Holmes (2014) demonstrated that there is a "low to moderate correlation between coverage and effectiveness" of test suites, meaning that beginners who rely on coverage numbers as their sole quality indicator are likely to be misled about the actual fault-detection capability of their tests. Bai et al. (2021) observed this misconception in practice, reporting that students "believe code coverage is the most important outcome" of unit tests despite the evidence that coverage poorly predicts fault detection (Bai et al., 2021; Inozemtseva and Holmes, 2014). Without a structured visual representation that links coverage metrics to the corresponding source code and to the regression history of the project, students cannot develop an accurate mental model of what their tests are actually exercising.

[] The aim of this project is to design and develop a GUI-based automated testing software specifically for Python small scale projects. It integrates unit testing, regression testing, and code coverage analysis. By providing these features, it can lower the barrier for testing adoption in academic and small-scale development contexts.

[] To design and implement an integrated, automated testing workflow for Python applications that seamlessly supports the execution of unit tests and regression test suites, thereby reducing the configuration overhead for small-scale projects.
[] To develop a Graphical User Interface (GUI) that simplifies test configuration and provides intuitive visual feedback on both test execution results and code coverage analysis, reducing the cognitive load typically associated with command-line interfaces.
[] To provide an automated test case generation function that assists users in creating basic unit tests, reducing the manual effort and knowledge barrier associated with traditional test design.
[] To implement and validate an end-to-end testing workflow that automates regression verification and provides interactive visual feedback for coverage interpretation, eliminating the cognitive burden of CLI outputs.

[Heading3] Introduction
[] In modern software development, automated testing tools have become an indispensable part of the development workflow. This is necessary to address increasingly complex systems and ensure software quality. Indeed, a variety of testing frameworks and utilities have been developed within the Python ecosystem. They support unit testing, regression testing, and code coverage analysis. These tools provide developers with powerful capabilities to automate test execution and evaluate the effectiveness of test cases.
[] However, the practical adoption of these tools among beginners and students remains limited. Existing tools are typically designed around command-line interfaces, requiring users to manually manage configurations, dependencies, and tool integrations. Consequently, testing workflows can become fragmented, making it difficult for beginners to utilize these tools effectively. Furthermore, the lack of intuitive visual interfaces and guided interactions further reduces the usability of these tools in educational settings.
[] To better understand these challenges, it is necessary to examine both the fundamental concepts of software testing and the characteristics of existing tools. This chapter will start with the theoretical foundations of unit testing, regression testing, and code coverage analysis. It then analyses the current Python testing frameworks and tools. Finally, usability considerations in software engineering are discussed.
[Heading3] Concept of Unit Testing
[] Unit testing is one of the software testing techniques that should be learned by major developers. This technique is used to verify the correctness of the smallest parts of the software system. The smallest parts normally can be a function, a class or a method. According to Introduction to Software Testing (2016), unit tests are designed to validate the logic of a single part of a program in isolation. 
[] The unit testing has the characteristics of isolation which ensures the independence of the test case. Those tested units have been isolated from the external dependencies such as databases, file systems or other modules. This characteristic improves the reliability and repeatability of the testing.
[] A fundamental aspect of unit testing is the use of assertions. Assertions are used to verify whether the actual output result is matching with the expected result. In the practical Python development, testing frameworks such as pytest use the function of assertions to determine the success or failure of  test cases. 
[Heading3] Test Case Generation
[] Test case is a set of input, steps and expected results developed to determine whether the function or system meets the specified requirement. Traditionally, developers manually design and create test cases. Manual test case generation relies on the experience and knowledge of developers to design the appropriate test scenarios. This led to the issue of time-consuming and human error when there are large amounts of test cases needed to be generated manually.
[] Therefore, besides generating test cases manually, developers start to implement automated test case generation approaches. Automated test case generation uses algorithms and context to generate test cases. There are different techniques such as random testing, model-based testing, search-based testing and AI-assisted test generation. Automated test case generation helps to reduce the manual effort and increase the efficiency and the coverage of testing.
[Heading3] Concept of Regression Testing
[] Regression testing is the process of re-testing some parts of a system that has been modified. It constitutes a significant portion of testing effort in commercial software development and is considered an essential part of a reliable development process (Ammann & Offutt, 2016, p. 25). Small changes in one part of a system may introduce unexpected issues in other parts. To reduce the exposure of defects after release, the regression testing necessary to detect them.
[] As software systems grow in complexity, it will take a long time to execute all test cases. Therefore, techniques such as test case selection, prioritization, and test suite minimization are commonly used to improve efficiency while maintaining adequate coverage. Manually re-running a large number of test cases is inefficient and error-prone. To address this issue, automated testing frameworks enable rapid and consistent execution of regression tests. 
[] Although regression testing is often associated with CI/CD pipelines in industrial practice, it is also valuable in educational environments. For students, regression testing helps ensure that newly implemented changes do not break previously working functionalities. This is particularly important as novice programmers may lack systematic testing practices. In this project, regression testing is applied in a simplified and automated manner to support continuous validation of generated test cases.
[Heading3] Code Coverage Analysis
[] Code coverage analysis is a software testing metric. It used to measure the extent to which the source code of a program is executed during testing. It provides an indication of how much the system has been tested. It is identifying the parts of the code that have been exercised by test cases. The higher code coverage means the higher completeness of testing. However, this does not guarantee the absence of defects.
[] Common types of code coverage include statement coverage, branch coverage, and path coverage. Statement coverage measures whether each line of code has been executed. Branch coverage evaluates whether all possible decision outcomes including the possible true or false conditions of function. Path coverage considers all possible execution paths within a program. It is rarely used for complex systems due to the exponential number of paths.
[] Code coverage analysis is useful in identifying the under-tested parts of a system. By highlighting areas of low coverage, developers can improve test effectiveness by designing additional test cases to cover the remaining parts. In practical Python development, code coverage is commonly measured using automated tools such as coverage.py. These tools provide detailed reports on executed and unexecuted code segments. These tools also are often integrated into testing workflows to support continuous evaluation of test quality.
[Heading3] Python Testing Ecosystem
[] Nowadays, the Python programming language already has a mature ecosystem and library for manual or automated testing. These tools or frameworks support different testing needs. These tools generally support test execution frameworks, test generation libraries and code coverage analysers. In industry, these tools are widely used to make testing faster and more efficient. However, the configuration and setup are too complex and challenging for students and novice developers. 
[Heading4] Text Execution Library Comparison
[] Test execution library is used to define and execute the testing. The common Python libraries include unittest, nose2 and pytest. In the current practical industry, pytest is the dominant choice in practice among them. PyPI statistics show significantly higher downloads for pytest compared to nose2 (PyPI Download Stats, n.d.-a; PyPI Download Stats, n.d.-b). This disparity highlights the dominant position of pytest in practice.

[Heading4] Code Coverage Tools
[] In Python, coverage.py is commonly integrated with pytest to automatically collect execution data and generate coverage reports. These reports list out the percentage of code executed and highlight untested areas. 
[] However, coverage.py presents results in command-line or static formats, which may not be intuitive for beginners. Interpreting coverage outputs often requires prior knowledge, limiting their usability in educational contexts. Thus, there is a need for a more accessible approach to presenting coverage information. This motivates the integration of coverage analysis into a graphical interface.

[Heading2] SYSTEM DESIGN
[Heading3] High-Level Architecture Design
[] This section outlines the core technologies adopted in the proposed system and illustrates their integration to form a cohesive software architecture. As illustrated in Figure 4.1, the system is decoupled into three primary runtime environments, unified by the Tauri v2 framework.
[] Tauri v2 serves as the foundational framework that unifies the entire application stack. It provides a bridge between the frontend and the backend. The core feature of Tauri framework is to allow us to build lightweight, ultra-fast, and highly secure applications by combining modern website frontend technologies with a Rust backend.
[] Vue 3 framework serves as the graphical user interface. It provides an interactive dashboard for project management and test-related features. This layer is responsible solely for UI rendering and user interaction handling. All business logic and heavy computation are offloaded to the backend.
[] Rust serves as the central system of the application. Built with Tauri v2, Rust exposes a secure, type-safe IPC interface to the frontend. This layer is responsible for all business logic and system orchestration. It receives IPC commands from the frontend and manages the full application lifecycle. It also manages local caching, project state, and file system interactions.
[] Python serves as the isolated execution engine. It leverages the libraries for test execution, metrics collection, and automated test generation. It does not run as a persistent service. The Rust backend starts Python subprocesses on demand and communicates through standard input and output. This design reduces resource usage and isolates execution. It also ensures clean process termination after each task.
[] The persistence component manages all long-term data retention, including project configurations, test execution history, coverage caches, and user settings. By abstracting data storage into a dedicated component, the system ensures that the core orchestration logic remains agnostic to the underlying storage mechanism. Therefore, it can enhance the maintainability and extensibility.

[Heading3] Component Interaction
[] This section details the dynamic collaboration between the core system components during the primary workflow. As the software targets students and novice developers, the interaction flow is designed to minimize manual configuration and provide continuous visual feedback. The system relies on an asynchronous, event-driven communication pattern to ensure UI responsiveness across all operations. The component interaction is formed by four phases that represent the complete user journey which are Test Environment Setup, Automated Test Generation, Test Execution, and Coverage Analysis. 
[Heading4] Test Environment Setup
[Heading6] Figure 5.2: Sequence Diagram of the Environment Setup.
[] Upon project import, the Vue frontend sends an Inter-Process Communication (IPC) command to the Rust backend to validate the selected directory. The Rust core scans for the Python interpreter and virtual environment to verify the availability of required dependencies. Then, it initializes a dedicated persistence layer in local storage. The configuration status is then returned to the UI, prompting the user to install missing dependencies if necessary, or confirming a ready-to-test state.
[Heading4] Automated Test Generation
[Heading6] Figure 5.3: Sequence Diagram of the Automated Test Generation.
[] When the user selects a target Python module and initiates generation, the Rust backend invokes Pynguin library. The generation progress is streamed asynchronously to the UI via event-driven updates. Upon completion, the generated test files are safely written to the test directory by the Rust backend. The success notification containing the file path is displayed on the frontend which requires zero manual file handling from the user.
[Heading4] Test Execution
[Heading6] Figure 5.4: Sequence Diagram of the Test Execution.
[] When the user triggers test execution, the Rust backend spawns a Python subprocess invoking pytest library. Crucially, instead of adopting a synchronous blocking model, the Rust backend incrementally reads the standard output stream. It parses each line of execution logs in real-time and pushes structured updates to the Vue frontend via event emission system. This asynchronous design guarantees the UI to update the progress indicator and test dashboard continuously without freezing.
[Heading4] Automated Coverage Analysis
[Heading6] Figure 5.5: Sequence Diagram of the Automated Coverage Analysis.
[] After a successful test execution, the Rust backend automatically triggers coverage.py library in subprocess to collect statement and branch coverage data. The raw coverage output is parsed into a structured JSON format by the Rust layer and cached in the local storage. A coverage-ready event is then emitted to the frontend, which renders an interactive code viewer, highlighting covered and uncovered lines based on the parsed metrics, thereby closing the feedback loop for the user.
[Heading3] Database and Data Storage Design
[] To implement the long-term data retention, the persistence layer utilizes a hybrid storage approach. Structured metadata such as projects, execution history, and regression suites, is managed via an embedded SQLite database integrated into the Tauri. Heavy or unstructured historical data, such as raw code coverage metrics parsed from coverage.py,  are stored as serialized JSON files in the system local application data directory to maintain UI responsiveness and high performance.
[Heading4] Multi-Project Data Isolation Strategy
[] The strict data isolation strategy is enforced to prevent historical test metrics and virtual environment configurations from overlapping between different local Python projects. Each imported project is assigned a unique Snowflake ID. The system creates isolated subdirectories within the application data folder.
[Heading4] Entity-Relationship Diagram
[] The Project table stores metadata for imported local projects. The Test Execution History table saves pass-rate statistics from each executed test. The Regression Suite table holds user-saved execution parameters for one-click reruns. Lastly, the Coverage Results table stores overall coverage metrics while mapping them to the specific local JSON cache files.
[Heading6] Figure 5.6: Entity-Relationship Diagram.
[] Entity Relationship Logic Description:
[] A Project has a one-to-many relationship with TestExecutionHistory, meaning one project can have multiple test execution records.
[] A Project has a one-to-many relationship with RegressionSuite, meaning one project can contain multiple regression suites.
[] A RegressionSuite has a one-to-many relationship with TestExecutionHistory, meaning one regression suite can generate multiple execution histories.
[] A TestExecutionHistory has a one-to-zero-or-one relationship with CoverageResults, meaning one test execution may generate zero or one coverage result.

[] This interface serves as the central workspace where users can manage imported projects, review testing status, and access important project information before executing automated testing tasks. The dashboard is divided into three main sections which are navigation area, project management area, and status bar area.
[] The left navigation area provides quick access to the major functions of the system. The "Import Project" function allows users to add a local Python project into the system. The "Clone Repository" function enables users to retrieve projects from remote Git repositories. Additionally, the "AI Test Generator" option provides access to the automated test generation feature supported by Pynguin. The resource section contains supporting features such as documentation, issue reporting, and system settings.
[] The main area displays a list of available projects managed by the system. Each project is presented with necessary testing information such as project name, environment status, latest test results, test coverage, and the most recent execution time.
[] The Environment column provides users status of the project environment. An overview of the execution environment, such as the Python version, virtual environment status, and dependency availability. This helps users identify configuration problems before running tests.
[] The Last Test Result column summarizes the outcome of the latest testing execution by showing the number of passed and failed test cases. This allows users to quickly evaluate the current quality status of each project.
[] The Coverage column presents the test coverage percentage using a visual progress indicator. This provides users with an immediate understanding of how much of the source code has been tested.
[] The bottom status bar area provides global system information. It displays the currently detected Python version, total number of registered projects, and the total number of testing executions performed by the system. This helps users understand the current software environment and overall system usage.
